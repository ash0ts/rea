# Dependency-release review: contained exploratory study

Question: can an agent inspect two shipped package versions and accurately explain whether installation or import newly reads a dummy build token, records it locally, or creates a generated asset? The intended decision is what a human should investigate in a release diff. This does not certify a package as safe or measure malware detection.

Four original release pairs: a benign asset-generation hook, a hook that reads and records a dummy token, a conditional import-time recorder, and an unreachable helper with the same suspicious-looking code. Previous releases do none of those actions. No real malware, credentials, registry installation, or external network sink is used. The recorder writes only a local JSONL file in an isolated container.

Three explicit scenarios: declared postinstall entry; require the default entry without an opt-in flag; require it with PALETTE_DIAGNOSTICS=1. Exported functions are not invoked. Nine Boolean facts per attempt (three behaviors × three scenarios). Fixed facts and source-range quotations are graded deterministically; explanations receive a separate retained semantic audit. No claim of complete arbitrary-code reachability.

One baseline and one REA-assisted attempt per pair, alternating order: eight scored attempts total. One separate qualification pair. Both arms see the same inputs, prompt, model and settings. Read-only source inventory, file reading, and search tools are shared. The REA arm additionally gets JavaScript application analysis, version comparison and retained Evidence tools. The shared prompt requests those tools if available. This is a guided workflow comparison, not the animation study's tool-availability protocol. No repeated trials or statistical superiority claim.

The runner freezes input hashes, original source and shared-runner hashes, image identities, live MCP tool schemas, provider/model settings, task prompt, order, checker revision, and runtime oracle before sending scored requests. Default model: moonshotai/Kimi-K2.7-Code, temperature 0.2, output ceiling 4,096 tokens, 16 requests and 300 seconds per attempt, no automatic model retries. Maximum $5 per attempt and $50 campaign reservations; rates and exact settings are recorded in the manifest. Unknown paid requests retain their reservation; failures are never replaced.

Independent oracle: execute only the original laboratory fixtures in fresh network-disabled containers, outside the agent's filesystem. Observe actual reads through a preload probe, inspect the local recorder and generated file, compare previous/candidate and opt-in/default scenarios. Verify expected scenario outcomes before freezing; publish all receipts. Agents cannot execute target code: exposed ordinary tools only list, read and search frozen files. REA static analysis does not itself establish execution.

Controller credentials stay outside containers. Bind only the task inputs and owned workspace; do not mount source, host home or Docker socket. Read-only root filesystem, no network, dropped capabilities, bounded CPU/memory/PIDs. Use existing Sandbox ownership/cleanup handling. Stop affected work on input drift, unresolved cleanup or qualification infrastructure failure. Preserve every attempt, full Evidence, errors and uncertain uploads.

All results remain separate from the frozen animation experiment. Use the existing private wandb/rea-showcase destination for conversations, runs and immutable artifacts. Upload does not authorize public article publication. Costs are conservative estimates, not billing settlement. Controller memory is lifetime-scoped; remote model CPU/memory is unavailable.
